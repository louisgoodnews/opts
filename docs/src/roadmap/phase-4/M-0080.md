## 🎯 Objective

The user controls how much of the map is resident: either **everything** (*Load all tiles on start*) or a **radius of tiles around the centre tile** (the tile the player camera stands on), with a default that adapts to the machine.

## 📦 Deliverables & Tasks
- [x] **Setting `Load all tiles on start`** (`gameplay.load_all_tiles`, bool, default off): all map tiles are force-loaded during loading and **kept resident** (no eviction, no streaming-out) for the whole session. Registered in the settings registry (generated reference, control protocol `settings.*`).
- [ ] **Exposed in the *Plan a drive* summary** (Review step, [wizard](../phase-9/wizard-and-loading.md)): the same setting as a visible switch with a plain-language note (loading time and memory use; an estimate from the tile count and the hardware profile, e.g. 'about 2.1 GB, 40 s'); changing it there changes the global setting (or offers *only for this drive* — decision recorded in the milestone); the loading screen shows real progress per tile.
- [x] **Setting `Tile radius`** (`gameplay.tile_radius`, integer ≥ 1, step 1, max from the map size): number of tiles loaded around the centre tile (1 = 3×3, 2 = 5×5, …); applies live (streaming adjusts without restart). Disabled with the reason when *Load all tiles* is on.
- [x] **Dynamic default:** when the user has not chosen a value, the radius is derived from the hardware profile of `opts-hardware` (GPU class and VRAM, free system memory, CPU threads, storage speed class) through a documented, tested function (`recommended_tile_radius(&HardwareProfile, &MapStats)`); the settings page shows 'Automatic (currently 3)' and a *Reset to automatic*.
- [ ] Memory guard: when *Load all tiles* would exceed a safe share of available memory the UI warns (red text per the UI standards) and offers the radius mode; never silently crash or swap.
- [x] Streaming uses hysteresis so the radius does not thrash at tile borders (existing paging rules kept).
- [x] Control protocol: `settings.*` cover both; `scene.tiles` reports loaded/resident tiles, radius and mode.
- [x] Docs: update `docs/src/architecture/` streaming page and the settings reference; tests for radius math, force-load retention, live change, wizard exposure.

## ✅ Acceptance Criteria
- With *Load all tiles* on, every tile of a test map is resident after loading and stays resident while the camera moves across the map (test and control-protocol check); with it off, only the radius around the centre tile is resident.
- The default radius differs between two synthetic hardware profiles (test) and is explained in the UI; the summary screen shows and changes the all-tiles switch.

## 📝 Progress

- 2026-10-29 (`agent/tile-controls`, first slice): the numbers for the two open UI items exist in `opts-hardware` as `estimate_load_all` (memory of all tiles, loading time as a range, memory verdict against `safe_resident_mib`; tests in `recommend/load_all/tests.rs`; [hardware probe](../../architecture/hardware-probe.md) §5). Loading time comes from the loading-stage figures of [streaming performance](../../architecture/streaming-performance.md) §2 (0.085 to 0.31 s per tile, measured on an SSD; a spinning disk is flagged as unmeasured). The memory per tile is still the `MapStats` default of 120 MiB, **not measured** ❓: a measurement per map would sharpen the "about N GB" text. Open: the Review-step switch and note, the red warning that offers the radius mode, and the "Automatic (currently N)" label; the checkboxes above stay open until they are wired in.

## 🧭 Plan for the three open UI items (2026-10-29, traced through the code)

Nothing below is built yet. The numbers for the first two already exist (`estimate_load_all`, above).

1. **Summary switch with the estimate** (wizard Review step). `step_review.rs::spawn_review` builds from a `BuildCtx` (`new_game_screen/mod.rs`, constructed in `mod.rs` twice and in `systems/list_events.rs`) that has no settings or hardware profile: add `&GameSettings` and `Option<&HardwareProfile>`. A row below the choices card: a switch bound to a new `PlannerAction::SetLoadAll(bool)`, handled in `systems.rs::handle_actions` by writing `gameplay.load_all_tiles`; the note shows the tile count of the chosen map (`Info::Map.tile_count` of the catalogue), the memory and the time range from `estimate_load_all` (the tile size is still the unmeasured 120 MiB default ❓). The screen must also rebuild when the setting changes (today it rebuilds on the planner state). Messages `wiz-load-all-*` in the wizard's en and de tables.
2. **Memory guard.** For `MemoryVerdict::TooLarge`, red text (`ColorRole::Error`) and a button *Use the tile radius* (`SetLoadAll(false)`); `Unknown` shows no warning, only the estimate.
3. **"Automatic (currently N)".** `settings_screen/rows/controls.rs::spawn_control` writes an integer as its number, so the tile radius shows `0`. A per-key special case would add to a function that is already over the 80-line limit; the clean way is a small descriptor hook ("zero means automatic, with this text") used by the row builder. `recommended` in `in_game/tile_loading.rs` gives N.

**Decision to record.** The switch changes the **global** setting `gameplay.load_all_tiles` (the milestone's first wording: "the same setting as a visible switch"), not a per-drive or per-map override; the map-profile design ([map profiles](../../architecture/map-profiles.md)) could carry it per map later. **Tests to expect to touch:** the wizard tests, the accessibility and HUD matrices, the golden screens at three sizes (their layouts change), and the localisation checks (every key in both languages, no literals).
