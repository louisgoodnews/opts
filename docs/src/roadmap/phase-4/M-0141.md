## 🎯 Objective

A player can operate a vehicle the way its manual says: switch the electrics on, start and stop the engine, work lights, indicators, doors, wipers, heating and ventilation, the parking brake and the gear selector, with every button and switch of the dashboard that has a function reacting, and the instruments and warning lights showing what the vehicle's scripts compute. Each reference vehicle gets a **start procedure** that is written down, reached through the controls OPTS offers (keys and the mouse in the cockpit), and checked by a test.

---

## 🔍 What exists, and the gap (2026-10-20)

**Exists:** the keys of `keyboard.cfg` raise the scripts' triggers ([M-0045](M-0045.md)); mesh hot-spots (`[mouseevent]`) react to click, drag and release in the cockpit and passenger views, with `mouse_x`/`mouse_y` while held; the scripts run and drive the vehicle ([M-0097](M-0097.md)); `vehicle.key`, `vehicle.keys` and `vehicle.script_vars` in the control protocol; the lamps and animations the scripts drive ([M-0045](M-0045.md)).

**Gap found live (Citybus 530, `01a_o530_e2_2.bus`, Ahlheim 5), corrected 2026-10-20:** the bus did not start from a cold start through the mouse (the drag trigger fired once, so the ignition key could not turn: fixed) and the first reading of its scripts missed that `kw_m_enginestart` is handled in `cockpit.osc` (it steps the ignition key back; the battery key steps it forward, so E, E, E starts the engine from the keyboard). The engine sounds ([M-0102](M-0102.md)) follow once the engine runs. Nothing in the roadmap owned "the vehicle can be operated": M-0045 delivers the trigger plumbing, M-0097 the torque once the engine runs, M-0101 the doors' passenger side.

---

## 🔍 Scope

**In scope:**

- **Electrics:** battery master switch, ignition, busbar voltage (`elec_*`), consumers that depend on it.
- **Engine:** the start procedure per vehicle (battery, ignition key positions, starter, interlocks such as gear in neutral, parking brake, doors), idle, stop; the `engine_*` variables the scripts expect from the host.
- **Lights and signals:** headlights, high beam, parking light, fog lights, indicators, hazards, interior lights, brake and reverse lamps.
- **Doors:** the driver's door switches and their effect on the door scripts (open, close, release, kneel), door state indicators.
- **Heating, ventilation, air conditioning:** the controls and the fan and heater state (`cp_*heiz*`, `klima*`, fans) as far as the scripts expose them.
- **Wipers and washers**, horn, parking brake, gear selector and retarder controls.
- **Dashboard:** every button, switch and rotary control with a `[mouseevent]` reacts (click, drag, scroll where the script reads it); instruments (speed, rpm, pressure, fuel) and warning lights follow the script variables; hover feedback (the name of the control under the cursor) so a player can find them; a list of a vehicle's controls through the protocol.
- **Verification:** a scripted start procedure per reference vehicle in the rig (Citybus 530, MAN NL, SD200, NG272, C2, one tram) as acceptance, and a controls report listing triggers no control raises and controls whose trigger no script handles.

**Out of scope:** passenger flow and tickets ([M-0101](M-0101.md)), the displays' content ([M-0100](M-0100.md)), AI scripts ([M-0103](M-0103.md)), rebinding UI beyond what exists ([M-0035]), force feedback and sound ([M-0102](M-0102.md)).

## ✅ Acceptance Criteria

1. For each reference vehicle the start procedure is documented and its test goes from a cold vehicle to a running engine (`engine_on` 1, `engine_n` at idle) using only controls the player has (keys, hot-spots).
2. In the running game, on the Citybus 530, the engine can be started and stopped with the mouse in the cockpit; the engine sounds of [M-0102](M-0102.md) follow. *(Start verified 2026-10-20 through `vehicle.click`: `engine_on` 1, idle 598 rpm, idle loop audible; stopping and the real mouse path still to be looked at.)*
3. Lights, indicators, doors, wipers and heating each have a verified control per reference vehicle; a switch with a function does something the player can see or hear.
4. The controls report lists every unhandled trigger of the reference vehicles with a decision (stubbed, remapped, out of scope).
5. `./scripts/local-ci.sh` passes; no OMSI asset is committed.

## ⚠️ Risks & Mitigations

| Risk | Mitigation |
| :--- | :--- |
| Each vehicle has its own procedure and variable names | Start from the reference vehicles; write the per-vehicle facts down; keep the host generic and put differences in data (a mapping table), not in code branches |
| Some start logic needs engine-side behaviour (starter torque, voltage) the host does not simulate | The rig shows what the scripts compute from which inputs; feed the inputs the scripts own, never overwrite their outputs |
| No OMSI to compare with | Procedures are read from the scripts and the manuals (add-on PDFs may be read, facts only); the project lead's look is the final acceptance |
