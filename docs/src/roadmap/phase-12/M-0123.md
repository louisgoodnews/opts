## 🎯 Objective

A vehicle's fuel (diesel) or battery (electric) charge depletes with engine load, the engine loses torque at empty, the level is visible on the dashboard and HUD and readable by the vehicle script, and it survives a session save. The player chooses how much of this applies: **Off**, **Realistic** or **Accelerated** consumption (the golden rule: the user has the choice).

**What exists already (build on it, do not duplicate), verified 2026-10-18:**

- The stock engine script already models consumption: [vehicle functions](../../simulation/vehicle-functions.md) lists the engine macro `engine_consumption` with variables `engine_tank_content` and `tank_percent` (written, `engine_GN.osc:275`) and the engine-raised trigger `veh_tank` for refuelling (`engine_GN.osc:129`); `tank_percent` has 305 script uses (L.L and S.L; [predefined variables](../../formats/text/vehicles/predefined-variables.md)). OPTS declares `tank_percent` as an output with **no consumer** (`crates/opts-sim/src/script/inputs.rs`, `Consumer::None`).
- Electrics are script-driven: `elec_busbar_main` (22,693 uses) and the constants `elec_busbar_minv`; with the battery switch off every electrical output is zero ([osc guide](../../formats/text/vehicles/osc-guide.md) electrics section). `crates/opts-bevy/src/vehicle_script.rs` already raises the battery-switch and start triggers for a driver. The engine start physics (`engine_starter`, `engine_n`) are in the same page of vehicle functions.
- Session save registry with sections ([session save](../../architecture/session-save.md), `crates/opts-game/src/save/registry.rs`): a new `SaveSection` joins without touching the container.
- `[petrolstation]` is a documented scenery keyword that makes the neighbourhood usable for refuelling and washing ([community cross-check](../../formats/community-crosscheck.md)); no code uses it.
- Unknown (❓, settled in the audit, not guessed): the semantics and unit of `engine_tank_content` and of the tank capacity constant; which variable (if any) carries an electric vehicle's state of charge (no `battery_*` or `soc` name is in the predefined-variable list; electrics are the bus-bar voltage); whether the stock scripts themselves cut torque at an empty tank; whether `veh_tank` is raised by the vehicle or expected from the host.

---

## 🔍 Scope

**In scope:** (a) audit of the corpus: which vehicles use `engine_tank_content`, `tank_percent`, `veh_tank`, which electric vehicles expose a charge, capacity constants and typical consumption; (b) a host-side `FuelState` model for vehicles whose scripts do not (or for the Accelerated multiplier) with a clear rule for who is authoritative; (c) torque cut at empty (diesel: engine stops; electric: traction power limited), with a warning stage at low level; (d) variables exposed to the VM: `tank_percent` (and the real tank/charge variables found in the audit), `veh_tank` trigger handling; (e) HUD and dashboard indication (a HUD gauge entry plus the model's own gauge through the script variable); (f) diesel versus electric by vehicle data; (g) setting *Fuel and battery*: Off / Realistic / Accelerated (multiplier documented); (h) save and restore via a session-save section; (i) tests and docs.

**Stretch (decision recorded at the audit, default out of scope):** refuelling at `[petrolstation]` objects. The audit decides between "refuel by command/menu while stopped" (in scope as the minimum, so a vehicle at empty is not stuck) and placing refuelling at stations (stretch, follow-up milestone). Charging stations for electric vehicles are out of scope.

**Out of scope:** fuel price or money, engine damage from running dry, battery temperature or ageing, regenerative braking efficiency modelling beyond what the scripts compute, traffic AI fuel.

## 📦 Deliverables & Tasks

- [ ] Audit table (Notes): per vehicle family the relevant variables, constants, and who computes consumption; ❓ resolved by experiment or kept as ❓ with a fallback.
- [ ] `FuelState` component (level 0..1, capacity, kind: diesel / electric) built from vehicle data with a documented default for vehicles that define nothing.
- [ ] Consumption: depletes with engine load (throttle times `engine_n`/torque for diesel, power draw for electric) at a documented rate; setting multipliers Off = 0 (infinite), Realistic = 1, Accelerated = documented factor.
- [ ] Torque cut at empty and a low-level warning; the state is also readable through the control protocol (`vehicle.fuel` query and set, for tests).
- [ ] VM exposure: write the audit's real variables each frame (`tank_percent` at minimum); handle `veh_tank` if the audit shows the vehicle raises it.
- [ ] HUD: gauge (follows the HUD registry pattern) with a low-level indicator; visible only when the setting is not Off; accessible without colour alone.
- [ ] Refuel minimum: Alt-menu or key action *Refuel* when stopped (and the stretch decision for `[petrolstation]` recorded).
- [ ] Save section `fuel` (versioned) holding the level per session vehicle; restore tests; missing section means full.
- [ ] Tests: consumption integral, multipliers, torque cut, save round trip, setting Off.
- [ ] Docs: new `docs/src/simulation/fuel-battery.md`, update `vehicle-functions.md` OPTS notes, settings reference, session-save sections table.

## ✅ Acceptance Criteria

1. With the setting Realistic, a diesel bus at constant full throttle for a simulated hour (fast-forward test) uses the documented amount within 5 %; at idle it uses the documented idle rate; with Accelerated the same run uses the documented multiple; with Off the level never changes.
2. At level 0 the engine torque is cut to zero within one frame (diesel) or limited to the documented fraction (electric), the vehicle coasts, and a refuel action restores the level and torque.
3. `tank_percent` in the VM equals the model's level x 100 within 0.5 for a test vehicle; if the audit finds a different variable for an electric vehicle, that variable is exposed too.
4. The HUD gauge reflects the level and the low-level indicator appears at the documented threshold; with the setting Off the gauge is hidden.
5. Saving mid-drive and restoring gives the same level (equal within 1e-4); an old save without the section restores a full tank.
6. With the setting Off, the behaviour of every existing vehicle test and the replay determinism tests ([determinism & replays](../../architecture/determinism-replays.md)) is unchanged.

All gates pass (`cargo fmt`, `cargo clippy -D warnings`, `cargo test --workspace --all-features`, `./scripts/local-ci.sh`); no unsafe code; no OMSI asset committed.

## ⚠️ Risks & Mitigations

| Risk | Mitigation |
| :--- | :--- |
| Two authors of the level (the stock script and the host) disagree | Audit first; one authoritative owner per vehicle family, the other read-only; test both paths |
| Stock scripts cut or ignore fuel differently | Host torque cut applies only where the script does not already stop the engine; documented per family |
| Electric charge variable unknown | ❓ stays visible; fall back to a host-side model driven by power draw and the bus-bar state |
| Running empty frustrates players | Default setting documented by the project lead; Off available; low-level warning; refuel minimum in scope |
| Determinism and replays | Fuel is part of the deterministic state; Off keeps behaviour identical |
