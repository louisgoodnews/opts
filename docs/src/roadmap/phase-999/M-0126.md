## 🎯 Objective

The standing procedure by which a refactoring cycle runs at the end of every development cycle, and the release gate that the last cycle before a public version has to pass, are written down, put into the prompt library as a process prompt and linked from the release process, so that any session can run a cycle the same way and the project lead approves it at the same checkpoints.

---

## 🔍 Scope

**In scope:** (a) the **cycle protocol**: the four phases of the task (audit with M-0125, plan with triage and batches, execution one batch per session with its gates, verification with the comparison table and the public-API diff), the checkpoints at which the project lead approves, the rules of the phase README, the failure handling (revert rather than force a split); (b) the **cycle template** `docs/src/roadmap/phase-999/CYCLE-TEMPLATE.md` from which a session creates the milestone `M-NNNN — Refactoring cycle <n>`, with the before and after table and the batch list; (c) the **process prompt** `docs/dev/prompts/process/P-1015-refactoring-cycle.md` (the task's prompt, current, with the guardrails), indexed in the prompt library README and referenced in `workflow.md`; (d) the **release gate**: a checklist in `docs/src/contributing/release-process.md` (a section of its own while the rest stays unwritten) with the conditions before a `v0.x.0` tag: the audit ratchet is not worse than at the last cycle, no file over the limit without a recorded justification, the public-API diff against the last release is reviewed, `docs/crates/*.md` match the tree, the cycle report exists; (e) a note in `CONTRIBUTING.md` and `docs/src/contributing/standards.md` (section 3.7) pointing to the cycle; (f) the BOARD convention that a cycle is announced there so no feature work touches the target files.

**Out of scope:** executing a cycle (M-0127 to M-0129); versioning policy and changelog (the rest of the release process); automating the refactorings.

## ✅ Acceptance Criteria

1. A session that has only the prompt P-1015 and the template can start a cycle: it knows the checkpoints, the gates and where each report goes (checked by the dry run, which makes no judgment call the prompt does not answer).
2. `release-process.md` has the release-gate checklist and every condition can be checked with a command or a file named there.
3. The prompt library index, `workflow.md`, `CONTRIBUTING.md` and `standards.md` link to the protocol; `check_links.py` passes.
4. The dry run's refactoring is behaviour-neutral (tests unchanged and green), has before and after counts in its commit, keeps the public path by re-export and passes `local-ci.sh`.

All gates pass (`cargo fmt`, `cargo clippy -D warnings`, `cargo test --workspace --all-features`, `./scripts/local-ci.sh`); no unsafe code; no OMSI asset committed.

## ⚠️ Risks & Mitigations

| Risk | Mitigation |
| :--- | :--- |
| The protocol is too heavy and gets skipped | One batch per session, each independently mergeable; the gate is a short checklist of commands |
| A cycle collides with feature work | The BOARD announcement and the "quiet tree" precondition; a batch touching a file in flight waits |
| The gate becomes a rubber stamp | Its conditions are numbers and diffs (ratchet, public-API diff), not opinions |
