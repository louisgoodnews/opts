## 🎯 Objective

The first refactoring cycle splits the files over the 500-line limit whose concern boundaries are clean (batch 1) or somewhat tangled but with few external callers (batch 2) into concern-named modules, without a change of behaviour and with the public paths intact. The plan (audit, triage, per-file proposals) is written first and approved; the splits follow one file per commit.

---

## 🔍 Scope

**In scope:** the cycle-1 audit and refactoring plan (`docs/src/architecture/refactoring-plan.md`, per file: the concerns with line ranges, the proposed files with estimated sizes, the risk, the tests affected); batch 1 and batch 2 as the plan defines them from the baseline (candidates by size and concern clarity: the data-format modules such as `opts-core/src/formats/scenery/sco.rs` and `opts-cli/src/commands.rs` (a table of command declarations), `opts-gui/src/components/combobox.rs`, `opts-bevy/src/model.rs`, `opts-bevy/src/weather.rs`; the plan decides); moving each file's tests with its code; `//!` documents on every new `mod.rs`; the after report.

**Out of scope:** files whose public API is used across many crates or that sit on hot paths (M-0128); crate-level changes (M-0129); behaviour changes and bug fixes (noted on the BOARD, not done here).

---

## 📦 Deliverables & Tasks

- [ ] Cycle-1 audit report (M-0125's tool) committed and the plan `refactoring-plan.md` approved at the project lead's checkpoint.
- [ ] Batch 1: every file of the batch split along its concerns; `git mv` where a file keeps its main concern, the rest as new files; re-exports at the old paths; before and after line counts in each commit message.
- [ ] Batch 2: the same, one file per commit, with the tests of each file moved with their code.
- [ ] Every new module has a `//!` document and no `mod.rs` is a bare list of re-exports.
- [ ] The public-API diff (`cargo public-api` or the manual diff) shows no removed items; changed paths listed with how callers keep compiling.
- [ ] The after table in the cycle milestone notes: files over 500 lines before and after, the largest file, functions over 80 lines (unchanged unless a split exposed one).
- [ ] The ratchet file updated: entries removed for the files that now comply.

---

## ✅ Acceptance Criteria

1. Every file of batches 1 and 2 is under 500 lines of code or has a recorded justification (a lookup table, a fixture) in the ratchet file.
2. `cargo test --workspace --all-features` and `./scripts/local-ci.sh` pass on every commit of the batch (each commit builds and tests green); golden screens and golden rig files are unchanged.
3. The public-API diff against the pre-cycle tag or commit lists no removed item; every moved item is reachable at its old path.
4. `git log --follow` works for the main file of each split.
5. The batch report states per file the before and after line counts and one sentence of justification; a refactoring that did not come out cleaner was reverted and is listed with the reason.
6. No behaviour change: no test was edited to make it pass; no new `unwrap`, `unsafe` or dependency.

All gates pass (`cargo fmt`, `cargo clippy -D warnings`, `cargo test --workspace --all-features`, `./scripts/local-ci.sh`); no unsafe code; no OMSI asset committed.

---

## ⚠️ Risks & Mitigations

| Risk | Mitigation |
| :--- | :--- |
| A split along line ranges instead of concerns | The plan names the concern of each part; review at the checkpoint; revert if it is tangled |
| Hidden callers break at the old path | Re-exports plus a workspace-wide `cargo check` per file; the API diff |
| Merge conflicts with feature work | The quiet-tree precondition; a file under a branch is postponed, not forced |

3. Batch 2 (tangled, few callers): the same with a test run per commit.
4. Update the ratchet; write the batch report in the cycle notes; merge each batch after approval.
