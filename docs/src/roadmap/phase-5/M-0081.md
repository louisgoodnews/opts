## 🎯 Objective

A new crate **`opts-hardware`** researches the machine's capabilities in depth — enough to choose sensible defaults (tile radius, texture filtering, look, UI scale, DLSS availability, audio device) — **without spying on the system**: local-only, minimal, no identifiers, nothing leaves the machine.

## 📦 Deliverables & Tasks
- [ ] **Privacy charter first** (`docs/src/architecture/hardware-probe.md`, ADR): collect only *capability* facts needed for a decision; **never** serial numbers, MAC addresses, user or host names, installed software lists, file listings, network configuration, location or any persistent unique identifier; **no network access** in the crate (enforced by a dependency check in CI: no HTTP/socket crates); results are kept in memory and in an optional local profile file the user can inspect and delete; **no telemetry**; the *Report an issue* dialog may attach the profile only after showing it to the user and with a checkbox; document exactly which fields exist (a generated reference page) so the surface is auditable.
- [ ] Crate structure: `HardwareProfile` (versioned, serialisable) with sections `cpu` (model class, physical/logical cores, ISA features relevant to us, cache sizes), `memory` (total/available RAM), `gpu` (vendor class, device class/tier, VRAM, driver capability level, supported wgpu features and limits, ray tracing/DLSS/FSR capability flags), `display` (resolution, refresh rate, scale factor, HDR support, count — no EDID serials), `storage` (class of the content drive: SSD/HDD/unknown by measured throughput, free space), `audio` (device present, channel layout), `input` (gamepad/wheel present as yes/no and kind), `os` (family and version class, display server, container/VM hint). Every field is `Option` with a reason when unknown.
- [ ] Probes via platform APIs and `wgpu` adapter info where available (Linux first: `/proc`, `/sys` reads limited to an allowlist of paths; Windows and macOS stubs documented as planned); every probe has a time budget (whole probe ≤ 500 ms, longer ones such as the storage benchmark are explicit, optional and cached) and fails soft.
- [ ] **Deep research without spying**: a documented *analysis* mode (`opts-tools hardware report`) prints the full profile to the terminal for the user; an optional micro-benchmark set (CPU single/multi-thread, memory bandwidth, GPU fill/compute, storage read) measures real capability instead of guessing from model names, run only on request or at first run with a visible progress and cancel; results stored locally with a fingerprint-free hash of the *hardware class* only.
- [ ] **Recommendations API**: pure functions from `HardwareProfile` to defaults (`recommended_tile_radius`, `recommended_texture_filtering`, `recommended_look`, `recommended_ui_scale`, `dlss_available`) with tests over a table of synthetic profiles; consumers in the settings registry show 'Automatic (currently …)'.
- [ ] Settings: *Settings → Advanced → Hardware*: shows the profile, *Re-detect*, *Delete stored profile*, *Allow including the profile in reports* (default off); control protocol `hardware.profile`.
- [ ] Tests: schema round trip, redaction test (a scan of the serialised profile for forbidden patterns: MAC, UUID, hostname, username), no-network dependency check, timing budget, unknown-field handling.

## ✅ Acceptance Criteria
- The generated field list and the charter agree; the redaction test passes on real and synthetic profiles; `cargo tree -p opts-hardware` contains no networking crate; the full probe takes ≤ 500 ms on the reference machine without benchmarks.
- Tile radius, texture filtering and look defaults react to profile changes in tests.
