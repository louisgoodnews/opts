## 🎯 Objective

Reproducible CPU baselines for the code that runs on every load and every tick: the OMSI text parsers and the vehicle physics step. A change that makes loading or the tick slower should show as a number, not as a feeling.

## 🔍 Scope

**In scope:** Criterion benchmarks in `opts-benchmark` (renderer-free: `--no-default-features`) on **synthetic** input written for the benches, so no OMSI asset is committed and the numbers do not depend on an installation; the recorded baseline with the machine it came from; how to run them.

**Out of scope:** GPU benchmarks (`opts-hardware`, [M-0081](M-0081.md)); frame-time and streaming measurements in the running game (the [streaming performance](../../architecture/streaming-performance.md) traces); a CI gate on timings (shared runners are too noisy for that, see below).

## 📦 Deliverables & Tasks

- [x] *(2026-10-29, `agent/criterion-bench`)* Criterion as a development dependency of `opts-benchmark` with default features off (no plotting stack); `cargo-deny` passes.
- [x] `benches/parsers.rs`: the tile (`MapTile::from_text`, 500 and 5,000 objects), the scenery object (`SceneryObject::from_text`, 5 and 60 meshes) and the bus manifest (`BusManifest::parse`, 3 and 40 axles). Every generator is checked once per run, so a generator that stops producing what the parser reads cannot give a meaningless fast number.
- [x] `benches/physics.rs` (feature `physics`): one `VehicleSimulation::step` of a standard bus at the 64 Hz tick, at rest, accelerating and cruising in a curve.
- [x] *(2026-10-29, `agent/bench-mesh`)* `benches/meshes.rs`: the `.o3d` parser on a synthetic plain version-1 mesh of 1,000, 10,000 and 40,000 faces (the layout of the parser's own self-authored sample, scaled). It is the plain path only: most installed meshes are newer versions and many are keyed (scrambled) and take the exact decoder, so this is a lower bound, not the cost of a real vehicle.
- [x] *(2026-11-05, `agent/m0028-bench`)* The `.o3d` parser on newer versions and on keyed meshes, and the `.x` parser. `benches/meshes.rs` now writes every layout from the format page: version 1, version 7 (32-bit counts) with 16-bit and with 32-bit face indices, and keyed version-7 meshes scrambled by the exporter model `o3d::exact::scramble` and timed as the loader reads them (parse, then `o3d::exact::decode`); the run checks once that a keyed mesh is scrambled and decodes back to the plain positions. `benches/xfiles.rs`: the text `.x` parser (`parse_x`) on a `Frame` with one mesh, normals, a material list and texture coordinates in the format page's example layout, 1,000 and 10,000 faces. The binary `.x` form (26 of 8,145 files, unspecified, Q-X03) is not measured.
- [x] *(2026-10-29, `agent/bench-configs`)* `benches/configs.rs`: the map manifest (`global.cfg`, 100 and 2,000 tiles) and the vehicle model configuration (`model.cfg`, 30 and 300 meshes with a material, a visibility rule and an animation each).
- [x] *(2026-11-05, `agent/m0028-bench`)* The spline profile (`.sli`) parser: `benches/splines.rs` writes the layout of the format page's minimal example (shortened from a real file; the page is 🟢 Specified): height profiles, textures, `[profile]` with `[profilepnt]`s and `[path]`s, with 4 profiles (a typical road by the corpus keyword counts) and 40.
- [x] *(2026-11-05, `agent/m0028-bench`)* A regression check against the recorded baseline: not in CI (shared runners vary by far more than a regression); `scripts/bench_compare.py` compares two runs of `<target>/criterion` on one machine (Criterion's `slope` estimate, else the mean). A case regresses when it is slower than the threshold (5 %) and the two 95 % confidence intervals do not overlap; exit 1 on a regression. Tests: `scripts/test_bench_compare.py` (in `local-ci.sh`). Usage in the [crate guide](../../../crates/opts-benchmark.md). Checked by running the `configs` bench twice on unchanged code while another session's game ran: the two runs differed by −31 % to +53 % per case, so the check reported two regressions. Compare only on a quiet machine.

## ✅ Acceptance Criteria

1. `cargo bench -p opts-benchmark --no-default-features --bench parsers` (and `--bench configs`, `--bench splines`, `--bench meshes`, `--bench xfiles`) and `cargo bench -p opts-benchmark --no-default-features --features physics --bench physics` run and print a time and a throughput per case.
2. No OMSI asset is needed or committed.
3. The baseline below names its machine.

All gates pass (`cargo fmt`, `cargo clippy -D warnings`, `cargo test --workspace --all-features`, `./scripts/local-ci.sh`).

## 📊 Baseline (2026-10-29)

Machine: Intel Core i9-11900K (8 cores, 16 threads), 3.5 GHz, release profile, run alone under the build lock (no other build of ours ran); Criterion's default sampling. The figures are for comparison on the same machine, not absolute promises.

| Case | Time | Throughput |
| :--- | ---: | ---: |
| `tile/500_objects` | 448 µs | 94 MiB/s |
| `tile/5000_objects` | 4.47 ms | 96 MiB/s |
| `scenery_object/5_meshes` | 2.98 µs | 137 MiB/s |
| `scenery_object/60_meshes` | 28.97 µs | 140 MiB/s |
| `bus_manifest/3_axles` | 2.26 µs | 260 MiB/s |
| `bus_manifest/40_axles` | 13.5 µs | 217 MiB/s |
| `global_cfg/100_tiles` | 19.9 µs | 134 MiB/s |
| `global_cfg/2000_tiles` | 352 µs | 158 MiB/s |
| `model_cfg/30_meshes` | 59.6 µs | 110 MiB/s |
| `model_cfg/300_meshes` | 513 µs | 128 MiB/s |
| `o3d_plain_v1/small_1k_faces` | 5.35 µs | 4.76 GiB/s |
| `o3d_plain_v1/building_10k_faces` | 55.2 µs | 4.59 GiB/s |
| `o3d_plain_v1/vehicle_40k_faces` | 575 µs | 1.76 GiB/s |
| `vehicle_step/at_rest` | 179 ns | |
| `vehicle_step/accelerating` | 192 ns | |
| `vehicle_step/cruising_in_a_curve` | 228 ns | |

What they say: a dense tile of 5,000 objects parses in under 5 ms, so parsing the text of a tile is a small part of a tile build (which costs 28 ms on average while driving, [streaming performance](../../architecture/streaming-performance.md) §2). The physics step costs about 0.2 µs against a tick of 15,625 µs: the simulation is not where the frame time goes. Throughput stays within 20 % across the sizes of each text parser (tile and scenery object within 3 %; bus manifest 217 to 260 MiB/s), so their cost is close to linear in the input. The mesh parser is as fast up to 10,000 faces (about 4.6 GiB/s) but drops to 1.8 GiB/s at 40,000 faces; why was not investigated (the working set leaving the cache is a guess ❓). *(2026-11-05: not the cache: with the new vertex data below there is no drop up to 120,000 faces. The old generator put every vertex on one plane (z = 0) with coordinates growing to 240 m; that input is the likely difference, not confirmed ❓.)* A plain 40,000-face mesh still parses in 0.6 ms. The map manifest of a city (2,000 tiles) parses in 0.35 ms and the model configuration of a large bus (300 meshes) in 0.5 ms: reading the configuration files is not where a load spends its time.

## 📊 Baseline addendum (2026-11-05)

Same machine and build profile, run under the build lock. The rustrim session shared the machine (load average 1.9 to 3.4 on 16 threads during the run; its builds wait on the same lock, its game may have been running), so these figures are less quiet than those above. The `.o3d` inputs have new vertex data (varied positions instead of one plane), so the v1 rows replace the ones above for comparison.

| Case | Time | Throughput |
| :--- | ---: | ---: |
| `sli/4_profiles` | 4.10 µs | 162 MiB/s |
| `sli/40_profiles` | 46.2 µs | 143 MiB/s |
| `o3d_plain_v1/small_1k_faces` | 4.84 µs | 5.26 GiB/s |
| `o3d_plain_v1/building_10k_faces` | 50.3 µs | 5.04 GiB/s |
| `o3d_plain_v1/vehicle_40k_faces` | 201 µs | 5.03 GiB/s |
| `o3d_plain_v7/building_10k_faces` | 49.9 µs | 5.08 GiB/s |
| `o3d_plain_v7/vehicle_40k_faces` | 201 µs | 5.05 GiB/s |
| `o3d_plain_v7_32bit/large_120k_faces` | 702 µs | 5.28 GiB/s |
| `o3d_keyed_v7/building_10k_faces` | 215 µs | 1.18 GiB/s |
| `o3d_keyed_v7/vehicle_40k_faces` | 758 µs | 1.34 GiB/s |
| `x_text/small_1k_faces` | 635 µs | 151 MiB/s |
| `x_text/building_10k_faces` | 8.47 ms | 120 MiB/s |

What they say: the version and the index width do not change the cost of a plain mesh (about 5 GiB/s from 1,000 to 120,000 faces). Decoding a keyed mesh costs about 23 to 27 ns per vertex on top of the parse, so a keyed mesh takes 3.8 to 4.3 times as long as a plain one (0.76 ms for a 40,000-face vehicle part). A text `.x` mesh is far slower than an `.o3d` of the same size: 10,000 faces take 8.5 ms against 0.05 ms (about 170 times), at the throughput of the other text parsers, so the cost is the text form itself. A spline profile parses in microseconds.

## ⚠️ Risks & Mitigations

| Risk | Mitigation |
| :--- | :--- |
| Synthetic input is simpler than real files and flatters the parsers | The sizes follow real files; the real corpus is covered by the corpus tests and by the scenery benchmark ([M-0054](M-0054.md)); a bench on real files is a later task |
| Timing noise on shared machines | Baselines are compared on one machine only; no CI gate |
