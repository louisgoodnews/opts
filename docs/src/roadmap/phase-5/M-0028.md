## 🎯 Objective

Reproducible CPU baselines for the code that runs on every load and every tick: the OMSI text parsers and the vehicle physics step. A change that makes loading or the tick slower should show as a number, not as a feeling.

## 🔍 Scope

**In scope:** Criterion benchmarks in `opts-benchmark` (renderer-free: `--no-default-features`) on **synthetic** input written for the benches, so no OMSI asset is committed and the numbers do not depend on an installation; the recorded baseline with the machine it came from; how to run them.

**Out of scope:** GPU benchmarks (`opts-hardware`, [M-0081](M-0081.md)); frame-time and streaming measurements in the running game (the [streaming performance](../../architecture/streaming-performance.md) traces); a CI gate on timings (shared runners are too noisy for that, see below).

## 📦 Deliverables & Tasks

- [x] *(2026-10-29, `agent/criterion-bench`)* Criterion as a development dependency of `opts-benchmark` with default features off (no plotting stack); `cargo-deny` passes.
- [x] `benches/parsers.rs`: the tile (`MapTile::from_text`, 500 and 5,000 objects), the scenery object (`SceneryObject::from_text`, 5 and 60 meshes) and the bus manifest (`BusManifest::parse`, 3 and 40 axles). Every generator is checked once per run, so a generator that stops producing what the parser reads cannot give a meaningless fast number.
- [x] `benches/physics.rs` (feature `physics`): one `VehicleSimulation::step` of a standard bus at the 64 Hz tick, at rest, accelerating and cruising in a curve.
- [x] *(2026-10-29, `agent/bench-mesh`)* `benches/meshes.rs`: the `.o3d` parser on a synthetic plain version-1 mesh of 1,000, 10,000 and 40,000 faces (the layout of the parser's own self-authored sample, scaled). It is the plain path only: most installed meshes are newer versions and many are keyed (scrambled) and take the exact decoder, so this is a lower bound, not the cost of a real vehicle.
- [ ] The `.o3d` parser on newer versions and on keyed meshes, and the `.x` parser: they need synthetic writers for those layouts.
- [ ] The map parsers beyond the tile (`global.cfg`, splines) and the model configuration.
- [ ] A regression check against the recorded baseline: not in CI (shared runners vary by far more than a regression); as a script that compares two `target/criterion` runs on one machine.

## ✅ Acceptance Criteria

1. `cargo bench -p opts-benchmark --no-default-features --bench parsers` (and `--bench meshes`) and `cargo bench -p opts-benchmark --no-default-features --features physics --bench physics` run and print a time and a throughput per case.
2. No OMSI asset is needed or committed.
3. The baseline below names its machine.

All gates pass (`cargo fmt`, `cargo clippy -D warnings`, `cargo test --workspace --all-features`, `./scripts/local-ci.sh`).

## 📊 Baseline (2026-10-29)

Machine: Intel Core i9-11900K (8 cores, 16 threads), 3.5 GHz, release profile, run alone under the build lock (no other build of ours ran); Criterion's default sampling. The figures are for comparison on the same machine, not absolute promises.

| Case | Time | Throughput |
| :--- | ---: | ---: |
| `tile/500_objects` | 448 µs | 94 MiB/s |
| `tile/5000_objects` | 4.47 ms | 96 MiB/s |
| `scenery_object/5_meshes` | 2.98 µs | 137 MiB/s |
| `scenery_object/60_meshes` | 28.97 µs | 140 MiB/s |
| `bus_manifest/3_axles` | 2.26 µs | 260 MiB/s |
| `bus_manifest/40_axles` | 13.5 µs | 217 MiB/s |
| `o3d_plain_v1/small_1k_faces` | 5.35 µs | 4.76 GiB/s |
| `o3d_plain_v1/building_10k_faces` | 55.2 µs | 4.59 GiB/s |
| `o3d_plain_v1/vehicle_40k_faces` | 575 µs | 1.76 GiB/s |
| `vehicle_step/at_rest` | 179 ns | |
| `vehicle_step/accelerating` | 192 ns | |
| `vehicle_step/cruising_in_a_curve` | 228 ns | |

What they say: a dense tile of 5,000 objects parses in under 5 ms, so parsing the text of a tile is a small part of a tile build (which costs 28 ms on average while driving, [streaming performance](../../architecture/streaming-performance.md) §2). The physics step costs about 0.2 µs against a tick of 15,625 µs: the simulation is not where the frame time goes. Throughput stays within 20 % across the sizes of each text parser (tile and scenery object within 3 %; bus manifest 217 to 260 MiB/s), so their cost is close to linear in the input. The mesh parser is as fast up to 10,000 faces (about 4.6 GiB/s) but drops to 1.8 GiB/s at 40,000 faces; why was not investigated (the working set leaving the cache is a guess ❓). A plain 40,000-face mesh still parses in 0.6 ms.

## ⚠️ Risks & Mitigations

| Risk | Mitigation |
| :--- | :--- |
| Synthetic input is simpler than real files and flatters the parsers | The sizes follow real files; the real corpus is covered by the corpus tests and by the scenery benchmark ([M-0054](M-0054.md)); a bench on real files is a later task |
| Timing noise on shared machines | Baselines are compared on one machine only; no CI gate |
