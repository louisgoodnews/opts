## 🎯 Objective

AI agents set **every** setting through the CLI as reliably as a user does through the settings page. Protocol 1.1.0 already has `settings.list/get/set/reset`; this milestone closes what is missing after verifying the reported gap.

## 📦 Deliverables & Tasks
- [x] **Reproduce the report:** state exactly which setting or call failed for the reporter (settings not listed, `opts-cli` subcommand missing, change not applied, restart-required, revert prompt blocking) and record it in the field report.
- [x] Settings that need the 15 s revert prompt (window mode/size): a `confirm` argument or `settings.confirm`/`settings.revert` so agents can finish the change; restart-required settings report `needs_restart`.
- [x] Batch set and profiles: `settings.set_many` (atomic, validation errors per key), `settings.export`/`settings.import`, `settings.diff` against defaults.
- [x] Coverage test: every registered setting is listed, gettable, settable and resettable through the protocol (enumerated from the registry, so new settings are covered automatically).
- [x] Non-registry configuration reachable: language, theme mode, UI scale, content folders (OMSI folder), HUD widget switches, keybindings once M-0035 exists.
- [x] Reference page and `help` stay generated from the descriptor table.

## ✅ Acceptance Criteria
- A scripted session sets every registered setting by name, reads it back and resets it; the coverage test fails when a setting is not reachable.

## 📝 Outcome (2026-10-18)

- **The gap, reproduced as far as it can be:** the report does not say which call failed, so a scripted session was written instead: for **every** registered setting (enumerated from the registry) `settings.list`, `get`, `set` to a different valid value, read back, `reset`. All of them pass; the typed stored keys of `GameSettings` are all registered too (`protocol_tests.rs`). What was missing, and is the likely gap behind the report: risky settings (window mode, resolution) were applied and saved with no way to confirm or revert them, a change did not say whether it needs a restart, and there was no batch or profile method.
- **Added (protocol 1.7.0):** `confirm` on `settings.set` and `settings.reset` with `settings.confirm` and `settings.revert` (the page's 15 s prompt, for scripts; one change waits at a time, the timeout reverts); `applied` and `needs_restart` in the answer of a change; `settings.set_many` (atomic, every refusal listed in `data.errors`), `settings.diff`, `settings.export` and `settings.import` (profiles, with `reset_missing`). Reference page regenerated from the command table.
- **Non-registry configuration:** language, theme mode, UI scale, the OMSI folder and the vehicle key bindings are registry settings (`interface.language`, `theme_mode`, `ui_scale`, `omsi_path`, `controls.vehicle.*`) and so reachable; HUD widget switches have their own `hud.*` methods. Gamepad and wheel rebinding does not exist yet (M-0035).
- **Not done:** the settings page's own prompt and a protocol change to the same setting can still overwrite each other when both are used at once (the protocol refuses `confirm: false` while the page's prompt waits, but not the reverse).
