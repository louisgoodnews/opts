## 🎯 Objective

LOTUS offers a plugin interface for a driver's desk, a set of switches and levers built as hardware. OPTS has no device interface for one: the control protocol is for tooling. Add a driver's desk interface, so that hardware switches and levers can drive the same actions as the keyboard.

## 🧩 Scope

Owner decision 2026-11-22: a driver's desk hardware interface is in scope, under this milestone. Gamepad and wheel stay in [M-0035](../phase-7/M-0035.md).

1. A design note for the device interface, shared with [M-0166](M-0166.md), built from the public documentation of the input APIs.
2. Each device input is bound to an action of the registry in [M-0142](../phase-7/M-0142.md), so that the same conflict and reset rules apply.
3. A test source stands in for the hardware in the test suite.

**Out of scope:** any OMSI or LOTUS input code or configuration files ([ADR-0002](../../adr/0002-clean-room-policy.md)).

## ✅ Acceptance Criteria

1. The design note exists and is reviewed together with [M-0166](M-0166.md).
2. A device input drives its bound action, and a test shows it (with the test source).
3. A device binding follows the conflict and reset rules of the registry (test).
4. A dated check with real hardware is recorded in the notes; until then the feature is marked untested on hardware.
