## 🎯 Objective

Profiles work without the editor: a hand-written or generated profile TOML changes a vehicle's sound set, script set, constants and meshes on top of the base OMSI vehicle, the vehicle selection lists it as a derived vehicle, and incompatible swaps are caught with warnings.

**Rules fixed by the task:** a **patch layer**: a `VehicleProfile` (TOML) wraps the base OMSI vehicle; OPTS reads the base `.bus` and `.cfg` and applies the profile on top. The OMSI installation is never modified: profiles live in OPTS's data directory (`~/.local/share/opts/vehicles/`). A profile that fundamentally breaks the vehicle (missing script variables, say) is never saved without a warning. No custom 3D editor engine: reuse Bevy's ECS and `bevy_picking` / `bevy_gizmos` where available, otherwise state the dependency (a new workspace dependency needs the project lead's approval). This is a tooling and customisation phase; it is not mixed with the simulation-realism phases.

---

## 📦 Deliverables & Tasks

- [ ] Parse and store `VehicleProfile` (schema of M-0135), profiles in `~/.local/share/opts/vehicles/`; the catalogue lists each profile as a derived vehicle (selection menu, Alt menu, `--vehicle-path` equivalent).
- [ ] Loader: base `.bus` and `.cfg` first, then the overrides: **sound** (the other vehicle's `sound.cfg` and `.wav` files), **scripts** (the other vehicle's `.osc` set and varlists merged or replaced as the design says), **constants** (`const_overrides` without editing base files), **meshes** (`target_mesh` → `new_mesh` with translation, rotation, scale applied to `origin_trans` / `origin_rot`).
- [ ] The validation layer of M-0135 A2 (variable lists and constants of both vehicles, sound variable dependencies, missing bones or pivots), warnings shown when a profile loads and when it is saved; a profile that fundamentally breaks the vehicle is not saved without an explicit confirmation.
- [ ] A fingerprint of the base files in the profile; a clear message when the base vehicle is missing or changed.
- [ ] Control protocol: list, load and validate profiles (`vehicle.profile.*`), documented in the reference.
- [ ] Tests: schema round trip; each override kind on fixture vehicles; the validation outcomes on the three vehicle pairs of M-0135; the OMSI installation is verified unchanged after loading.

---

## ✅ Acceptance Criteria

1. A profile swapping Bus B's sound set into Bus A loads and plays Bus B's sound with Bus A's geometry; one swapping scripts runs when compatible and warns (or blocks, per the design) when not.
2. A mesh override moves, rotates and replaces a mesh as written; the base files are never written to.
3. All gates pass (`cargo fmt`, `cargo clippy -D warnings`, `cargo test --workspace --all-features`, `./scripts/local-ci.sh`).
