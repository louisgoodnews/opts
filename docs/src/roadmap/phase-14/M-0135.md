## 🎯 Objective

The design of vehicle profiles and the visual editor, written down and approved before any implementation: the override schema, the compatibility validation, the editor architecture. **No implementation code** in this milestone.

**Rules fixed by the task:** a **patch layer**: a `VehicleProfile` (TOML) wraps the base OMSI vehicle; OPTS reads the base `.bus` and `.cfg` and applies the profile on top. The OMSI installation is never modified: profiles live in OPTS's data directory (`~/.local/share/opts/vehicles/`). A profile that fundamentally breaks the vehicle (missing script variables, say) is never saved without a warning. No custom 3D editor engine: reuse Bevy's ECS and `bevy_picking` / `bevy_gizmos` where available, otherwise state the dependency (a new workspace dependency needs the project lead's approval). This is a tooling and customisation phase; it is not mixed with the simulation-realism phases.

## 📦 Deliverables & Tasks

Read first: `docs/src/formats/text/vehicles/{bus,model_cfg,sound_cfg,varnamelist}.md`, [vehicle-scripts-route.md](../../architecture/vehicle-scripts-route.md); Bevy picking and gizmo documentation (if it is not in the codebase, it is recorded as an external dependency).

- [ ] A1 `docs/src/architecture/vehicle-profiles.md` and the format spec `docs/src/formats/vehicle_override.md`: the minimal `VehicleProfile` TOML that references a base vehicle: `[base] vehicle_path`, `[audio] sound_cfg`, `[scripts] script_set` and `const_overrides` (for example `engine_max_rpm`), `[[mesh_overrides]]` with `target_mesh`, `new_mesh`, `translation`, `rotation` (and scale); how it is parsed and applied during the vehicle load sequence (the base is loaded first, the profile patches it).
- [ ] A2 Compatibility validation: **scripts**: compare the base vehicle's variable list (`_varlist.txt`) and constants (`_constfile.txt`) with what the new script set requires, block or warn heavily on a mismatch; **sounds**: check that the new `sound.cfg` does not depend on variables the base engine script lacks; **meshes**: warn when a replacement `.o3d` lacks a bone or pivot that the base `[newanim]` entries expect. Severity levels (block, warn, info) and how a warning is shown and recorded.
- [ ] A3 Visual editor architecture: a new state (`AppState::VehicleEditor`) or a modal overlay on the paused game; picking (`bevy_picking` or a custom raycast) on the vehicle's meshes; translate/rotate/scale handles with `bevy_gizmos`; an asset browser panel in `opts-gui` over the catalogue's `.o3d` files; how changes become `[[mesh_overrides]]`; undo.
- [ ] A4 Report schema, validation and architecture to the project lead; **wait for approval before M-0136 and M-0137** (checkpoint).

**Points to settle in the design (found while documenting):** how a profile appears in the vehicle selection (a derived vehicle with its own catalogue entry, repaints and equipment options inherited from the base); how profiles of vehicles that are themselves profiles are handled (no chains in the first version); what happens when the base vehicle is missing or changed after the profile was saved (a stored fingerprint of the base files); how mesh overrides address meshes (by `model.cfg` mesh path, with the index for duplicates, since one `.o3d` can occur several times); sound and script swaps across vehicles of different generations (the `ST*` script-texture and callback sets differ).

## ✅ Acceptance Criteria

1. Both documents exist with a worked example for each override kind and for each validation severity.
2. The validation rules are checked against at least three real vehicle pairs (a compatible one, a script-incompatible one, a sound-incompatible one) on paper from the installation's varlists and constants (read-only).
3. The editor architecture names every Bevy feature it needs and its availability in the version the workspace uses, or the dependency to add.
4. The project lead has approved or amended the design.
