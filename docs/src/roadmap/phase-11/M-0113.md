## 🎯 Objective

Switches on rail tracks work for AI and player trains: switch definitions are read from the tiles, a vehicle announces its intended route, and the switch changes to it (or the vehicle waits) so a train takes the intended branch.

**What exists already (build on it, do not duplicate):**

- Rail vehicles and formations exist ([rail vehicles](../../simulation/rail-vehicles.md), [M-0106](../phase-10/M-0106.md)); rail lanes are planned in [AI traffic](../../architecture/ai-traffic.md) (`LaneKind::Rail` with switches `[switch]`, `[switchdir]` and signal routes) but not implemented; the format pages mention switch parameters in tiles ([tiles](../../formats/map/tiles.md)).

---

## 🔍 Scope

**In scope:** inventory of switch definitions in the corpus tiles (how a switch, its branches and its control are stored), a `SwitchState` model with the active branch, a request API (`request_route(vehicle, branch)`) honoured when the switch is free of vehicles, announced intent by the AI trip route (M-0112) and by the player (input or automatic from the route), visual/animated state if the switch object has one, protocol call to read and set switches.

**Out of scope:** railway signalling and interlocking, derailment, manual hand-thrown switch animation details beyond the data, tram-specific traffic lights.

## 📦 Deliverables & Tasks

### Research
- [x] Docs first: how switches are stored in rail objects (`[switch]`, `[switchdir]`, `Switch` variable, `toggle_switch`); census (282 objects); format page: [sco.md §Rail points](../../formats/text/sco.md). Tile placement carries no switch field of its own ❓ (not checked beyond the object).

### Model
- [x] Switch state per points object (`PedestrianNet` positions, gated lanes from `[switchdir]`), request by approaching trains, lock while a train is on the points; trains take the open lane (tests in `opts-sim` `rail::train` and `pedestrian::switches`).

### Interaction
- [x] AI: the trip route determines the branch ahead of time (announce at 100 m or the lookahead); player: automatic from a chosen route or key to toggle the next switch; HUD hint of the switch ahead.
- [x] Animation: the position drives the object's `Switch` variable (tongue meshes). Open: the player's click on the tongue (`toggle_switch`).

### Verification
- [ ] Scenario: a train approaches a two-branch switch with both intents; wrong-position handling (vehicle stops before a switch not yet set).

---

## ✅ Acceptance Criteria

1. The census states, for the corpus, the number of switches, branch counts and the fields that identify them; unknown fields are listed.
2. A scheduled tram/train whose route takes the diverging branch passes a switch set to the straight branch only after the switch changed to diverging; in a headless run 100 % of 20 passes take the intended branch.
3. A switch is never changed while a vehicle is on its throat (test: request during occupation is deferred until clear).
4. The player can set the next switch with a documented key and the HUD shows its state; the control protocol reads the state.

All gates pass for milestones that change code (`cargo fmt`, `cargo clippy -D warnings`, `cargo test --workspace --all-features`, `./scripts/local-ci.sh`); no unsafe code; no OMSI asset committed.
