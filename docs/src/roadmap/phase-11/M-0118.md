## 🎯 Objective

Know exactly which events the OMSI base engine raises, which events content adds, what parameters they carry and in which order they are dispatched, and decide how OPTS consolidates them into one event system instead of one ad-hoc channel per feature. Output is knowledge and a design, not code.

**What exists already (build on it, do not duplicate):**

- [M-0102](../phase-4/M-0102.md) already plans `ScriptEvent` messages from every part's engine, an audio subscriber and a list of engine-raised events (Q-BSI-4) stubbed explicitly; this milestone supplies the taxonomy and the ordering rules that M-0102 and M-0098 (trigger routing) currently assume or leave to experiment E8.
- [Bus script integration](../../architecture/bus-script-integration.md) and its [research report](../../meta/bus-script-integration-2026-10-14.md) describe triggers, `Snd_*` and the callbacks; the [callbacks reference](../../formats/text/vehicles/callbacks.md) lists the callback signatures.
- Triggers and events appear in `.osc` scripts, `sound.cfg`, `model_cfg` (`[mouseevent]`), `keyboard.cfg` and the passenger cabin files; no document yet collects them as one taxonomy.

---

## 🔍 Scope

**In scope:** inventory of every event source in the installation and the documentation we own (scripts, `sound.cfg`, `keyboard.cfg`, `model_cfg`, `.sco`/`.sli` scripts, map objects), event taxonomy (base-engine events versus content-added events), parameter formats (including string payloads such as `(T.F)` announcement files), dispatch and ordering/priority rules, and a consolidation design for OPTS (one typed event bus, mapping from OMSI names, extension points for content-added events).

**Out of scope:** implementing the event bus or any consumer (M-0102, M-0098, M-0115 do that), decompiling or inspecting OMSI binaries (ADR-0002: facts from data files, user-owned documentation and black-box experiments only), audio engine choice.

## ✅ Acceptance Criteria

1. `events.md` exists, lists every event name found in the three reference vehicles (NG272, SD200, HH109) and at least 95 % of the event names found in the corpus, each with origin class and parameter shape; unclassified names are listed explicitly, none silently dropped.
2. Every statement in `events.md` carries an evidence mark and a source (file class, corpus count or experiment id); no OMSI text, binary excerpt or asset is quoted or committed.
3. `event-system.md` states the dispatch order and priority rule in a form that a unit test could check, and names the three consumers (sound, trigger routing, tunnel/zone) with the event types each needs.
4. A table maps every acceptance-relevant item of M-0102 (Q-BSI-4 list) and M-0098 (trigger routing, E8) to a section of the new documents.
5. Docs-only milestone: `python3 scripts/check_links.py` and `mdbook build docs` pass.

All gates pass for milestones that change code (`cargo fmt`, `cargo clippy -D warnings`, `cargo test --workspace --all-features`, `./scripts/local-ci.sh`); no unsafe code; no OMSI asset committed.

## ⚠️ Risks & Mitigations

| Risk | Mitigation |
| :--- | :--- |
| Event names are partly runtime strings built by scripts | Census the literal names; mark computed names ❓ and propose an experiment instead of guessing |
| The base-engine event list cannot be read from data | Black-box experiments only (ADR-0002); keep the list open and design the bus so unknown events are logged, not dropped |
| Design drifts from M-0102 while that milestone is implemented | Review step in Phase C; M-0102 links to `event-system.md` before it starts |
