## 🎯 Objective

Decide whether and how OPTS can show real weather: which data providers, under which licences and with which offline policy, how observations map onto OMSI's `.owt` weather presets, where the location comes from, and what the fallback is. The deliverable is a document and a decision, not code.

**What exists already (build on it, do not duplicate):**

- [Weather](../../architecture/weather.md) is implemented from OMSI's own preset files (`Weather/*.owt`, `clouds.cfg`, `.dsc`): fog, clouds, precipitation, wet ground through the shared `Wetness`, script variables and four live settings; weather is part of `SessionEnvironment` and set from the wizard and the pause Environment page.
- The map's location is available from its world coordinates for `[worldcoordinates]` maps ([streaming coordinates](../../architecture/streaming-coordinates.md)); latitude already feeds the moon model ([lighting system](../../architecture/lighting-system.md)). Procedural weather is not part of weather.md and does not exist.

---

## 🔍 Scope

**In scope:** survey of at least three provider classes (public meteorological services with open data, commercial APIs, community/historical datasets) with licence terms, rate limits, privacy and cost; the offline policy (default offline, opt-in network access, caching, no keys in the repository); the mapping from observation fields (cloud cover, precipitation intensity/type, visibility, temperature, wind) to a `.owt` preset or a blend; the location source (map coordinates, user choice); the procedural fallback (a small deterministic generator driven by season/time) as design; the recommended provider(s) and a go/no-go.

**Out of scope:** implementing any network code, a procedural weather generator, changing the weather renderer, weather in the session save beyond what exists.

## 📦 Deliverables & Tasks

### Research
- [ ] Provider survey table: coverage, licence/attribution, commercial use, rate limits, historic data, auth model, privacy impact; verified from the providers' published terms with links and date.

### Mapping
- [ ] Define the observation-to-preset mapping on paper, tested against the install's preset list (names and parameters in `weather.md`) for 10 sample situations; define blending and rate of change.

### Policy and decision
- [ ] Offline/privacy/licensing policy, caching, user consent UI sketch; procedural fallback design; recommendation with alternatives.
- [ ] New file `docs/src/architecture/real-weather.md` with the decision and an ADR proposal; follow-up milestone drafts if the decision is go.

---

## ✅ Acceptance Criteria

1. `real-weather.md` contains the provider table with licence evidence and the date checked, and a recommendation that names one provider or states no-go with reasons.
2. The mapping table assigns each of the 10 sample situations to a concrete preset id or blend of existing presets, with no preset parameter invented.
3. The policy states: default behaviour offline, what is sent over the network (if anything), where keys live, how the user opts in; it passes a review against ADR-0002 and the project's privacy stance.
4. The procedural fallback design specifies inputs, outputs and determinism (same seed, same weather) in a form testable later.
5. Docs-only milestone: `python3 scripts/check_links.py` and `mdbook build docs` pass.

All gates pass for milestones that change code (`cargo fmt`, `cargo clippy -D warnings`, `cargo test --workspace --all-features`, `./scripts/local-ci.sh`); no unsafe code; no OMSI asset committed.

## ⚠️ Risks & Mitigations

| Risk | Mitigation |
| :--- | :--- |
| Provider terms change | Record the date and links; revisit at implementation |
| Licences forbid redistribution of data in an offline game | Prefer open-data providers; cache per user only |
| Mapping to presets is coarse | State error bounds; blends rather than hard switches |
