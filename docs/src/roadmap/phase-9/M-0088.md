## 🎯 Objective

Opening *Settings → Content* must never freeze the application. Any synchronous work that can block (catalogue queries, folder metadata checks for the scan chip, file-system probes, counting entities) runs off the main thread and the page shows a quiet placeholder until the result arrives.

## 📦 Deliverables & Tasks
- [x] **Reproduce and measure:** open the Content page on the 679,543-file / 75,313-entry catalogue; profile which calls block (suspects: `Catalogue::kind_counts`, the scan-status mtime walk over the OMSI folder and sub-folders, catalogue summary reads, texture-cache statistics).
- [x] Move every such call to a background task (Bevy `AsyncComputeTaskPool` / `Task` polled by a system, or a channel), deliver results through a resource or message; cache results with explicit invalidation (scan finished, folder changed); show skeleton/'Calculating…' text per row (de/en) and never block page build.
- [x] **Audit the whole UI** for other synchronous I/O or heavy queries in `Update`/`build` paths (settings pages, wizard lists, Home, Help, loading screen) with a source lint or a frame-time test that fails when a UI system exceeds a budget (interaction §10: ≤ 1 ms per frame); fix what it finds.
- [x] Rule in the standards: no file-system or database access on the main thread outside startup, except sub-millisecond cached reads.
- [x] Tests: a fake slow catalogue provider proves the page builds within one frame and fills in later; frame-time budget test.

## ✅ Acceptance Criteria
- Opening the Content page on the full catalogue does not drop a single frame above 33 ms (measured with the frame-time test and live); the numbers appear within a second or two without blocking.

## ✅ Result

- **Cause:** building the Content page ran `Catalogue::open` + `kind_counts` (joins over 75,589 entries), the texture-cache folder listing and, every 3 s, the scan chip's OMSI-folder walk and catalogue meta reads, all inside the page-build and chip systems. Measured on the full folder (692,725 files / 75,589 entries, release, warm disk): worst frame 213-350 ms per opening (a cold or slow disk or a running scan is much worse).
- **Fix:** [`content_facts`](../../../../crates/opts-game/src/content_facts.rs): a `FactsProvider` runs on a worker thread, the result arrives through a channel into `ContentFactsStore` (light facts every 3 s only while a page that shows them is open; heavy facts only after an explicit invalidation: scan finished, cache cleared, Settings opened). The four info lines and the scan chip show "Calculating…" / "Checking…" (de/en) until the answer arrives. The theme file list and Home's folder check use the same store; Home's picture is decoded in an `IoTaskPool` task, the drive history is read at startup and written by a writer thread, wizard thumbnails look for their source file inside the task, settings are saved by one background writer (`GameSettings::save_in_background`, flushed at exit).
- **After:** worst frame 16-18 ms opening Content (4 times), 20 ms with a rescan running, 24 ms returning to Settings; the numbers appear within a frame or two. Measured with the new `state.frame_ms_max` (worst frame of the last 10 s; control protocol 1.2, additive).
- **Guards:** `settings_screen::tests::the_content_page_builds_within_a_frame_and_fills_in_when_the_facts_arrive` (3 s slow provider, every frame < 250 ms), `the_scan_chip_says_it_is_checking_until_the_facts_arrive`, and the source lint `crates/opts-game/tests/no_blocking_ui.rs` with an explained allowlist; rule in [standards §3.13](../../contributing/standards.md).
