## 🎯 Objective

Opening *Settings → Content* must never freeze the application. Any synchronous work that can block (catalogue queries, folder metadata checks for the scan chip, file-system probes, counting entities) runs off the main thread and the page shows a quiet placeholder until the result arrives.

## 📦 Deliverables & Tasks
- [ ] **Reproduce and measure:** open the Content page on the 679,543-file / 75,313-entry catalogue; profile which calls block (suspects: `Catalogue::kind_counts`, the scan-status mtime walk over the OMSI folder and sub-folders, catalogue summary reads, texture-cache statistics).
- [ ] Move every such call to a background task (Bevy `AsyncComputeTaskPool` / `Task` polled by a system, or a channel), deliver results through a resource or message; cache results with explicit invalidation (scan finished, folder changed); show skeleton/'Calculating…' text per row (de/en) and never block page build.
- [ ] **Audit the whole UI** for other synchronous I/O or heavy queries in `Update`/`build` paths (settings pages, wizard lists, Home, Help, loading screen) with a source lint or a frame-time test that fails when a UI system exceeds a budget (interaction §10: ≤ 1 ms per frame); fix what it finds.
- [ ] Rule in the standards: no file-system or database access on the main thread outside startup, except sub-millisecond cached reads.
- [ ] Tests: a fake slow catalogue provider proves the page builds within one frame and fills in later; frame-time budget test.

## ✅ Acceptance Criteria
- Opening the Content page on the full catalogue does not drop a single frame above 33 ms (measured with the frame-time test and live); the numbers appear within a second or two without blocking.
