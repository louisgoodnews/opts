## 1. Character

> **A calm operations room, not a game menu and not a web app.**

OPTS is about real public transport. The interface should feel like the instruments and planning tools of a transit operator: quiet, precise, legible at a glance, with the *content* (maps, vehicles, the world itself) as the hero and the chrome staying out of the way. Four adjectives guide every choice:

| Quality | Meaning | Against |
| :--- | :--- | :--- |
| **Calm** | restrained colour, generous spacing, no decoration that carries no information | glass-on-photo effects that cost contrast (F09, F15) |
| **Precise** | strict grid, aligned numerals, consistent radii and weights | ad-hoc pixel sizes (F07, F23) |
| **Legible** | contrast and size first; readable at 4 m in a driving rig as well as at 60 cm | text below 12 px, grey on photo (F08, F09) |
| **Honest** | shows what is real; no placeholder data, no developer jargon | F05, F06 |

This is consistent with Phase 8: the 3D world is calibrated towards reality; the UI is the neutral frame around it.

## 2. Keep the token architecture, change its expression

*Decision D-UI-01.*

The three-tier token system (reference → system → component) is sound and live-themeable; **keep it**. What changes is what is built on top:

| Today | Proposed |
| :--- | :--- |
| "Material Design 3, strictly" as the visual identity | M3 is the *token vocabulary*, not the look. OPTS gets its own expression: squarer controls, denser layouts, a transit accent system |
| Pill buttons everywhere, glass on every surface | radius 8 px for controls, 12 px cards, 16 px sheets; pills only for chips and toggles; **glass only for overlays above the live 3D scene** (HUD panels, pause overlay), never on content screens |
| Menus over a blurred photo | photo as a *hero* in a defined region with a gradient scrim computed for contrast; the text area sits on a solid surface |

## 3. Theme

*Decision D-UI-02.*

| Theme | Use |
| :--- | :--- |
| **Dark** *(default, decided 2026-10-12)* | a simulator played in dim rooms and at night; matches the loading screen and HUD already in use; photos and the 3D scene read better against it |
| **Light** | for bright rooms and presentations |
| **High contrast** | contrast ≥ 7:1 for text, 4.5:1 for controls; the accessibility theme (UI-P10) |
| **System** | follows the operating system |
| **Auto (clock)** | light by day, dark by night using the device's local time and timezone, with configurable switch hours ([investigation](theme-auto-switch.md)) |

- **One theme for the whole application**, including loading screen, HUD chrome and dialogs (UI-P06, F10). Today's mix of a light application with dark hard-coded screens disappears.
- The instrument cluster in the HUD has its own **instrument token set** (§9), independent of the app theme but never hard-coded in widgets.
- The UI is drawn after tonemapping, so Phase 8's *Vivid / Natural* looks do not recolour it (to be verified in M-0061).
- **Accent**: default *Transit blue*; presets are generated by a function that picks `OnPrimary` and container colours to satisfy contrast automatically, replacing today's preset tables that fail it (Amber 2.15:1, Emerald 2.57:1; F09). Per-widget colouring is dropped: it multiplies combinations that nobody can keep accessible.

## 4. Colour

- **Roles**: keep the 34 M3 roles; add **semantic status roles** that M3 lacks: `Success`, `Warning`, `Info` (each with `On…` and container), used for loading results, validation and the editor.
- **Rules**: text and icons ≥ 4.5:1, large text and control borders ≥ 3:1 *measured on the rendered background*; `OutlineVariant` is decorative only (it measures 1.6:1 today); status is always icon + text + colour.
- **Colour-blind safety**: red/green are never the only distinction (parking brake, validation, signals); pairs are checked in a deuteranopia/protanopia simulation as part of the contrast test.
- **Transit colour**: line and livery colours (from repaints and, later, timetables) appear as small chips and left borders, not as backgrounds.

## 5. Typography

*Decision D-UI-03.*

| Today | Proposed |
| :--- | :--- |
| one face (DejaVu Sans Regular), 15 styles, line height and tracking never applied, 30 literal sizes below 12 px | **one family with ≥ 4 weights (400/500/600/700) and tabular figures**, 9 styles, line height applied, **no size below 12 px** at 100 % |

- **Selection criteria** for the family: open licence compatible with the repository (OFL), tabular lining figures (instrument readouts), German diacritics and a path to wider script coverage, ≥ 4 weights, good rendering at 12–16 px under Bevy's text stack. Candidates to evaluate in M-0061: *Inter*, *Noto Sans*, *IBM Plex Sans*; a monospaced companion for diagnostics (*JetBrains Mono* or *Noto Sans Mono*). The choice is a decision for the project lead after a rendered comparison.
- **Scale** (at UI scale 100 %): Display 40 (hero only), Headline 28, Title 20 and 16, Body 14 and 16, Label 12 (medium), Numeric 32/48 for instruments. Fewer steps than M3's 15; each step has one purpose.
- **Rules**: sentence case; units after numbers with a thin space; no all-caps strings except the 11–12 px overline labels; maximum line length 70 characters in descriptions.

## 6. Space, density, scale

- **4 px grid**, spacing tokens as today, plus **density modes**: *Comfortable* (default, controls 40 px), *Compact* (32 px), *Dense* (24 px, the editor only, as [workspace-ui](../../editor/workspace-ui.md) already assumes; `SpacingScale::Dense` does not exist yet).
- **UI scale 75–200 %** as a setting; the first run suggests a value from the display's pixel density. All layouts are expressed in tokens and flex rules, never fixed list heights (F07).
- **Layout classes** by window width: *Compact* < 900, *Medium* 900–1400, *Expanded* > 1400 logical px. Navigation rail: labels in Medium and Expanded, icons only in Compact. Master–detail screens stack in Compact. **Minimum window 1024×640** *(D-UI-04; today 800×600, at which several lists clip)*.
- **Alignment**: content on a 12-column grid with 24 px gutters; page margins 32 px (Expanded) / 16 px (Compact).

## 7. Shape, elevation, imagery, icons

- **Elevation**: a real shadow (Bevy's `BoxShadow`) plus a 1 px outline for floating layers (menus, dialogs, toasts), tonal tint on surfaces in both themes. Shadows are specified in today's design doc but do not exist (F24).
- **Imagery**: map `picture.jpg` is used at its native aspect ratio inside a hero region (`cover` crop, never stretched, never blurred by upscaling beyond 1.5×; a calm placeholder gradient otherwise). Vehicles and maps get **rendered thumbnails**, generated once and cached by the same thumbnail pipeline the editor's asset browser needs.
- **Icons**: one set, **Material Symbols (rounded, Apache-2.0)**, 16/20/24 px, every navigation item and every status carries an icon (today 13 glyphs exist). Icon-only buttons have tooltips.

## 8. Motion

*Principles UI-P04, UI-P10.*

- Durations from the existing tokens (100 / 250 / 400 ms); hover and focus 100 ms, panel and dialog 250 ms, screen change 400 ms, easing as defined. Nothing animates continuously except progress indicators.
- **Reduced motion** (setting and OS preference) replaces transitions by instant changes and disables parallax-style effects; the token exists and gets a consumer in M-0061.
- **No motion while driving** except instrument needles and unavoidable alerts.

## 9. The instrument and HUD look

*Principle UI-P13.*

A separate **instrument token set** (colours, sizes, numerals) used only by HUD widgets:

- large tabular numerals (speed 48, gear 32), generous letter-spacing between units, fixed widths so values do not jitter;
- **day and night variants** that follow the Phase 8 time-of-day; brightness never exceeds what the scene allows at night;
- translucent panels (the one legitimate use of glass) with a guaranteed minimum contrast against *both* a bright and a dark background, checked by rendering over the two extremes;
- semantic colours for warnings (parking brake, doors, faults) with icon and text;
- unit choice (km/h or mph), tidy defaults, and a hide/show model rather than a free-form layout for the first release (layout customisation arrives with the HUD registry, [expandability](expandability.md#3-hud-registry)).

## 10. What disappears

Glass on content screens; the developer copy of F05; the per-widget colour swatches; the "(Scrollable)" captions; the second copy of the New Drive summary; non-working features shown as buttons (Load Last Game until it exists); the permanent F10 block on the HUD (it moves into a developer panel that is off by default).
