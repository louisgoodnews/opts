## 🎯 Objective

Give every colour texture a correct mipmap chain. About 83 % of the corpus textures ship without one (≈ 120,000 JPEG/BMP/PNG/TGA files and 46,543 DXT files). **Hard limit (project lead, 2026-10-12): first-run work must never add more than 2 minutes** to loading a map.

---

## 📦 Deliverables & Tasks

### Phase A: Specification (this milestone file is the specification; refine before coding)
- [x] Decide the DXT path by measurement (**decided by the project lead 2026-10-25: option 2 with `texpresso` range fit and the derived cache**; measurement below): (1) decode to RGBA8 only, (2) decode → mips → re-encode to BC1/BC3 → derived cache, (3) anisotropy only. Candidate encoders to evaluate: `texpresso`, `intel_tex_2` (pure-Rust and build-time requirements decide). Record encode speed (MB/s) and quality (PSNR against the source's own level 0).
- [x] Cache design (accepted with the decision 2026-10-25): `~/.cache/opts/textures/<content-hash>-g<generator-version>.dds`, derived data on the user's machine only, never distributed; capped in size (default 4 GiB, least-recently-used eviction); invalidated by source hash or generator version; safe under concurrent processes (write to temp, rename).

#### Phase A measurement (2026-10-25)

Tools: `crates/opts-benchmark/examples/dxt_mips.rs` (corpus sample, one thread, release build) and the developer switch `OPTS_DEV_DXT_MIPS=count|rgba` (`opts_bevy::texture_filter::dev_dxt`; `count` logs the chainless block-compressed textures of a load, `rgba` applies option 1), with `scripts/visual-ab.sh` (dev profile, MAN SD77, noon, *Vivid*, 16×, three runs per setting). Machine: i9-11900K (8 cores), RTX 3060. Images and logs outside the repository (`~/.local/share/opts/benchmark/dev-dxt/`).

**Corpus:** 48,217 DXT1/3/5 files without a chain in the installation (more than the 46,543 of 2026-10-12; the installation grew). Sample of 400 (every n-th by path, 495 Mpx base); 28 of the DXT1 files have transparent texels (cutouts).

| Step (per texture, one thread) | Time | Quality of levels 1.. against the exact RGBA levels |
| :--- | :--- | :--- |
| Option 1: decode to RGBA8 | 2.8 ms (446 Mpx/s) | exact |
| Option 1: generate the chain | 4.4 ms | exact |
| Option 2 adds: `intel_tex_2` encode | 1.1 ms (1.5 GB/s) | RGB 38.5 dB; DXT3/5 alpha 49.8 dB; **DXT1 alpha 7.5 dB: its BC1 encoder drops the 1-bit alpha** (cutouts become opaque); no BC2 encoder |
| Option 2 adds: `texpresso` range fit | 8.0 ms (204 MB/s) | RGB 35.0 dB; DXT3/5 alpha 52.0 dB; DXT1 alpha 27.9 dB |
| Option 2 adds: `texpresso` cluster fit | 121 ms (14 MB/s) | RGB 36.7 dB; too slow |

**Per map (game, mean of three runs):**

| Map | Chainless DXT loaded | Load today | Load, option 1 | Visual effect of chains (high-frequency energy, 5 poses) |
| :--- | :--- | :--- | :--- | :--- |
| Bad_Huegelsdorf_2020 | 167 (63 Mpx) | 13.9 s | 14.7 s (+0.8 s, +6 %) | −4 to −14 %; subtle (distant pavement and cars calmer, foliage silhouettes kept) |
| Koeln | 125 (184 Mpx) | 13.1 s | 14.7 s (+1.6 s, +12 %) | **−14 to −61 %**; clearly visible: the grainy speckle on grass and asphalt in the middle distance is gone; signs, poles and trees intact; the grass's repeat pattern shows more |
| Grundorf | 0 | 12.2 s | 11.9 s (noise) | none (no chainless DXT in this map) |

Run-to-run noise of the metric was below 0.15 %. Köln's load times are measured to the end of loading (its load-problems dialog waits for a click). Stills only: shimmer in motion, where chains matter most, was not tested.

**Video memory (estimate from the pixel counts):** option 1 stores 5.3 bytes per base pixel (RGBA8 plus chain) instead of 0.5 (BC1) or 1 (BC3): on Köln about **+0.8 to 0.9 GB**, on Bad Hügelsdorf about +0.3 GB. Option 2 adds only the chain (+33 %): Köln about +30 to 60 MB.

**Cost against the 120 s budget:** cold option 2 with `texpresso` range fit on Köln: decode 0.5 s + chains 0.8 s + encode ≈ 1.0 s on one thread, about 2.3 s per load without a cache; with a warm cache the load reads ready DDS files (about today's time). That is 1–2 % of the budget.

**Decision 2026-10-25 (project lead): option 2 with `texpresso` range fit and the derived cache.** The recommendation was: option 2 with **`texpresso` range fit** alone (pure Rust, all three formats, keeps DXT1 cutout alpha; `intel_tex_2` is faster but loses cutouts and needs its prebuilt ISPC kernels). Because the measured cost is two orders of magnitude below the budget, phase C can drop the time-boxed worker pool and the budget cut-off; open choice: with the derived cache (saves ~2 s per Köln-size load, costs disk and invalidation code) or without (simpler, re-encodes on every load).

### Phase B: Uncompressed textures
- [x] `opts_bevy::texture::generate_mip_chain` (pure function): box downsampling (exact fractional area weights) with **sRGB-correct averaging**, correct handling of non-power-of-two sizes, optional alpha-coverage preservation (`MipOptions::alpha_cutoff`, used by [M-0059](M-0059.md); until then the loader switches it on for textures that *look like* cutouts, see `looks_like_cutout`).
- [x] Applied to JPEG/BMP/PNG/TGA/uncompressed DDS images at load time (`ContentLoader::texture`, the composed transparency-map textures, text textures) and in hot reload; textures that already have a full chain are untouched; skipped when *Texture filtering* is Off. **DDS chains silently dropped** (2,727 of 35,004, Q-TQ03) are fixed for block-compressed files too: the chain is re-laid out for the 4×4-rounded extent (`texture/dds_chain.rs`).
- [x] Tests: chain length and level sizes, sRGB averaging of a black/white checker (188, not 128), NPOT sizes, alpha untouched without coverage mode, coverage mode, cutout detection, DDS re-layout.
- Measured (dev profile, i9-11900K): about **2.4 ms per texture** on average over the textures of a scenery add-on (3,170 chains, 6.0 GB of base data in 7.6 s, ~800 MB/s); a 1024×1024 texture ≈ 7 ms. Bad Hügelsdorf with the MAN SD77: 230 chains in **1.0 s**; start-to-HUD load time **10.45 s → 11.13 s (+6.5 %)** over three runs each with the setting Off vs 16×. Details in `docs/dev/progress/visual-quality.md`.

### Phase C: Block-compressed textures and the budget
- [ ] Chain generation for DXT1/3/5 files without one (per the Phase A decision), writing the derived cache.
- [ ] **The 120-second budget** is enforced in code, not by hope: a time-boxed worker pool (`rayon`, bounded threads) processes the textures of a loading map in priority order (player vehicle, start tile, then by distance). When 120 s of *added* time have elapsed the loader stops waiting; remaining textures use the fallback (decoded RGBA8 with a GPU/CPU chain if the VRAM budget allows, else no chain with anisotropic filtering) and the cache keeps filling in the background at low priority. The loading screen shows progress; a log line reports used and remaining budget.
- [ ] VRAM budget: a setting and an automatic cap based on the adapter's memory; the loader never exceeds it (falls back to option 3 for the largest textures).
- [ ] The budget is configurable *downward* only (`--texture-budget-s`); the upper limit is 120.

## ✅ Acceptance Criteria
- **Cold cache:** loading each of the three reference maps adds **≤ 120 s** compared with today's load time on the reference workstation (measured, reported per map; a deliberately slowed encoder in a test proves the budget cut-off).
- **Warm cache:** load time ≤ 110 % of today's.
- High-frequency energy on the distance views drops further compared with M-0057 alone; no visible mip-level popping in a fly-through video check.
- Cache tests: invalidation on source change and generator-version change, concurrent writers, eviction at the cap, corrupted file ignored and rebuilt.
- All gates pass; `docs/crates/opts-bevy.md` documents the cache and the budget.
