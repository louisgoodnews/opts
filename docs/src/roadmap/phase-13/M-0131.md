## 🎯 Objective

An evidence-based proposal for splitting `opts-core` into native and legacy parts, written as `docs/src/adr/0014-data-model-separation.md` (Proposed), before any code moves. The project lead approves it at checkpoint 1.

**Rules fixed by the task (all milestones of the phase):** no circular dependency (shared domain types sit in a lower crate that both parsers use); `opts-sim`, `opts-bevy` and `opts-game` must not depend on `opts-omsi`; `opts-omsi` is a leaf adapter used by the importer; parser behaviour does not change (tests pass identically before and after); no OMSI parsing logic is deleted; files move with `git mv` so `git log --follow` works; no new workspace dependency without approval; nothing reaches `master` without the project lead's approval; checkpoints after phases A and B.

---

## 📦 Deliverables & Tasks

- [ ] A1 Audit `crates/opts-core/src/` into four buckets: shared math and geometry (coordinate transforms, mesh vertex structs), OMSI-specific parsers (the `.bus` keyword lexer, the `.o3d` chunk reader), OMSI-specific data (`BusManifest`, `ScoObject`), the abstract domain model (`VehicleDefinition`, `MeshAsset`, `PhysicsProperties`). Count the coupling: on 2026-10-19, 55 files of `opts-bevy`, 49 of `opts-game`, 20 of `opts-sim`, 7 of `opts-traffic` and 6 of `opts-benchmark` use `opts_core::formats::*`, and the game reads OMSI files at run time.
- [ ] A2 Three options: (1) two crates `opts-omsi` + `opts-model` with shared types in `opts-model`; (2) three crates `opts-types` (shared) + `opts-omsi` + `opts-model`; (3) a facade: `opts-core` stays, its implementation moves into `opts-omsi` and `opts-model`. One recommendation, justified by the dependency rules (the task expects option 2 or 3; option 1 tends to circular dependencies).
- [ ] A3 `Cargo.toml` dependency lists per crate: `opts-omsi` (`nom`, `binrw`, `opts-types`), `opts-model` (`serde`, `toml`, `opts-types`), `opts-bevy` (`bevy`, `opts-model`, `opts-types`, **no** `opts-omsi`), `opts-game` (importer, `opts-model`, `opts-bevy`).
- [ ] A4 Where the importer lives (the code that turns `opts-omsi` output into an `opts-model` TOML file): a new `opts-importer` crate or `opts-game`'s CLI.
- [ ] A5 Report to the project lead; **wait for approval before M-0132**.

**Open points the audit must settle (found while documenting this phase):**

1. The task states both that `opts-game` depends on `opts-omsi` "for the importer" and that `opts-game` must not depend on `opts-omsi`. Proposed resolution: the importer is a separate crate (`opts-importer`) that `opts-game`'s CLI calls; `opts-game` itself stays free of `opts-omsi`.
2. The game loads the OMSI installation directly at run time. Until a native format and an importer exist, the run-time loading path needs a home: an adapter crate that is allowed to depend on `opts-omsi` and produces `opts-model` values, or a temporary exception recorded in the ADR with the date it ends.
3. The Phase 999 milestone [M-0129](../phase-999/M-0129.md) also decides on crate splits and merges; this phase takes over the `opts-core` question, M-0129 keeps the rest.
