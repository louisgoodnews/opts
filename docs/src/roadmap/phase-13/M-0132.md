## 🎯 Objective

The new crates exist in the workspace and the shared domain types live in the lowest of them, with `opts-core` re-exporting them so nothing else breaks yet.

**Rules fixed by the task (all milestones of the phase):** no circular dependency (shared domain types sit in a lower crate that both parsers use); `opts-sim`, `opts-bevy` and `opts-game` must not depend on `opts-omsi`; `opts-omsi` is a leaf adapter used by the importer; parser behaviour does not change (tests pass identically before and after); no OMSI parsing logic is deleted; files move with `git mv` so `git log --follow` works; no new workspace dependency without approval; nothing reaches `master` without the project lead's approval; checkpoints after phases A and B.

---

## 📦 Deliverables & Tasks

- [ ] B1 Create the crate directories and `Cargo.toml` files chosen in the ADR (for example `opts-types`, `opts-omsi`, `opts-model`), add them to the workspace `Cargo.toml`, give each a `lib.rs` whose module comment states the crate's purpose.
- [ ] B2 Move the shared domain model and shared math into the base crate (`git mv`), update the imports in `opts-core`, keep temporary re-exports or type aliases in `opts-core`; `cargo check -p <base crate>` passes.
- [ ] `scripts/crate_graph.py` reports no cycle and the new edges; the structure-audit ratchet (M-0125) is updated if it exists by then.

---

## ✅ Acceptance Criteria

1. The workspace builds; all tests pass unchanged; `git log --follow` works on a moved file.
2. No crate depends on a crate above it; the base crate has no OMSI-specific item.
3. `opts-core` re-exports keep every existing `use` path working.
