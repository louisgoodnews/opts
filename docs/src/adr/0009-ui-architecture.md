# ADR-0009: UI architecture — one shell, layered library, registries, evidence-based principles

* **Status:** Accepted (2026-10-12); decision D-UI-09 amended: unavailable features stay visible with the red text "Feature not available yet!" instead of being hidden
* **Context:** The current UI is a set of separate full-screen screens built from hand-written node trees (16 builders of 150–345 lines). Hover, focus and keyboard activation exist only on the main menu; two visual systems coexist (themed screens and hard-coded dark screens); settings are hand-wired in five places; there is no localisation, UI scale, gamepad or accessibility support ([audit](../roadmap/phase-9/current-ui-audit.md)). Growth is certain: editor, mods, passengers, audio, more languages and input devices. A human-factors report supplied by the project lead provides the design rules ([analysis](../roadmap/phase-9/report-analysis.md)).
* **Decision:**
  1. **One application shell** with a navigation rail (≤ 5 main destinations plus Settings and Help); destinations appear only when they work.
  2. **A layered `opts-gui`**: tokens → core services → components → patterns; screens in `opts-game` are compositions of patterns. Dependencies point downward; all engine UI API stays inside `opts-gui`.
  3. **Registries for extension**: screens, settings (declarative descriptors that generate UI, persistence, CLI and documentation), HUD widgets and profiles, commands, themes, languages. Features register; the shell lays out.
  4. **An action layer** between devices and widgets; one focus model with a visible ring on every screen; pointer activation on release; Esc never destroys.
  5. **Keep the token architecture and the Bevy UI toolkit**; the visual identity becomes OPTS's own (see [design language](../roadmap/phase-9/design-language.md)), with one theme everywhere.
  6. **The principles UI-P01…UI-P13 are the acceptance checklist**, enforced by automatic tests over a UI tree (target sizes, contrast, keyboard traversal, no hard-coded colours or strings), golden screenshots and a moderated usability test.
* **Consequences:** + new screens, settings and HUD widgets cost one registration; + UI becomes testable without pixel coordinates; + accessibility and localisation are structural, not retrofits; − a substantial rebuild of the UI layer, staged in five milestones; − Bevy UI gaps (text input/IME, accessibility, virtualised lists, docking) must be spiked and may need purpose-built widgets; − existing documents (`gui-design-system.md`, `main-menu.md`) must be revised as the code changes.
* **Alternatives considered:** keep adding hand-built screens (cost grows with every feature, audit F23); adopt `egui` for tools (a second toolkit, a second look and theme system); a web-based UI (a different runtime, no benefit for in-game overlays); keep Material Design 3 as the visual identity (a generic look, glass-over-photo contrast problems).
